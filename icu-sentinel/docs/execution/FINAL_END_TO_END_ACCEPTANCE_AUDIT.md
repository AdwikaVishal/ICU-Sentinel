## 2. Reports data-integrity verification

### Root cause of zero-valued metrics

The Reports page (`icu-sentinel/frontend/src/pages/ReportsPage.tsx`) renders per-patient `total_hours`, `recorded_hours`, `missing_hours`, `observation_count`, and coverage from the `PatientListResponse` returned by `GET /api/v3/patients`.

**Defect found:** `DirectoryPatientRepository.list_patients()` (`ml/p3_temporal/replay/demo_data.py`) returned zeros for every patient because:

- `iter_processed_patients_from_directory` (the original loader) never populated `hour_min`/`hour_max` from the parquet files, so `list_patients()` took the `hour_min is None or hour_max is None` branch and set `total_hours = 0`, `recorded_hours = 0`.
- `observation_count` was hardcoded to `0` ("counted lazily per patient on demand" — but never actually computed).

This affected **all 40,336 patients** in the real PhysioNet-derived dataset.

### Fix applied

Added `_load_metrics_cache()` to `DirectoryPatientRepository.__init__()`, which reads a pre-computed JSON cache
(`icu-sentinel/data/reports/patient_metrics_cache.json`) generated by `compute_patient_metrics.py`. The cache was built by reading every patient parquet once (8-worker `ProcessPoolExecutor`, ~378 s for 40,336 patients) and computing:

| Metric | Definition |
|--------|------------|
| `total_hours` | Row count of the patient's hourly time series |
| `recorded_hours` | Rows with at least one non-null clinical observation (ICULOS excluded) |
| `missing_hours` | `total_hours - recorded_hours` |
| `observation_count` | Non-null clinical measurements across all clinical variables (ICULOS excluded) |
| `coverage` | `recorded_hours / total_hours` (percentage) |

ICULOS (time-in-ICU) is treated as metadata, not a clinical observation, per task requirements. `SepsisLabel`, patient identifiers, and other metadata columns are excluded.

If the cache is absent or corrupt, metrics fall back to zeros and individual patients can still be computed on demand via `_load_full_patient()`; no silent fabrication.

### Cache completeness

- Cache entries: **40,336** (matches manifest patient count exactly)
- Manifest patients subset of cache: **True**
- Patients in manifest but not in cache: **0**
- Patients in cache but not in manifest: **0**

### ICULOS inconsistency (defect fixed during this audit)

A second, related defect was found: `summarize_patient()` (used by `get_patient`/single-patient endpoint and `timeline.hour_summary`) iterated over **all** `CLINICAL_VARIABLES` including `ICULOS`, returning `observation_count=510` for p000001 (456 clinical + 54 ICULOS rows) — inconsistent with `list_patients()` (456, ICULOS excluded). The timeline `hour_summary.available_observation_count` and `observations` list also included ICULOS.

**Fix:** Excluded `ICULOS` from observation counts in:
- `ml/p3_temporal/replay/demo_data.py` — `summarize_patient()`
- `icu-sentinel/ml/p3_temporal/replay/timeline.py` — `hour_summary()` and `observations()`

Verified after fix: `get_patient(p000001)` returns `observation_count=456` (consistent with `list_patients`), timeline hour 1 shows `available_observation_count=3, unavailable_observation_count=36` (= 39 clinical variables), and the observations list contains 39 entries with no ICULOS.

### Cache staleness

The cache is a static JSON file generated by `compute_patient_metrics.py`. It does **not** auto-invalidate if source parquet files change. This is a documented limitation (see section 13). Cache freshness can be checked by re-running `compute_patient_metrics.py` and comparing the JSON.

Two distinct threshold concepts exist:

Note: The alert threshold (0.6 demo) differs from the model-specific validation thresholds (ET 0.04, XGB 0.69). This is an existing design separation, not a defect introduced here, but it is worth noting that alert firing depends on the demo threshold, not the model-optimized validation threshold.

## 13. Remaining limitations

1. **Cache staleness:** The patient metrics cache is a static JSON file. If source parquet files change, the cache becomes stale until `compute_patient_metrics.py` is re-run. No automatic fingerprint/timestamp invalidation is implemented. This is a known limitation; cache freshness can be checked by regenerating and diffing.
2. **All patients have complete data:** In this dataset every patient has `recorded_hours == total_hours`, so `missing_hours = 0` universally. The missing-hours code path is correct but not exercised by current data.
3. **Alert threshold vs model threshold:** The alert engine uses a demo threshold (0.6) distinct from the model-optimized validation thresholds (ET 0.04, XGB 0.69). Alert firing depends on the demo threshold.
4. **LightGBM not loadable:** LightGBM retraining crashes on this Windows machine (pre-existing C-library issue). LightGBM is not part of the frozen P2 results; this does not affect inference.
5. **Five-Page limitation:** Only five patients were independently verified against source parquets (p000001–p000005), though the cache covers all 40,336 and every cache entry was generated from source parquets by `compute_patient_metrics.py`.
6. **Performance not precisely instrumented:** Memory usage and exact API percentiles were not instrumented beyond observed response times.
